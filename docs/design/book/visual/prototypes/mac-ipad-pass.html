iPad: one structure, three window widths

iPad windows are resized by the person (Split View, Slide Over, Stage Manager), so the layout follows the window width, not the device. The same screens, three arrangements. Fewer modals and fewer full-screen transitions than on iPhone.

  • Adapt by window width. Use size classes and window width, not userInterfaceIdiom. The window can be resized live, so layouts must not break between states.
  • Add wallet is a form sheet, centred, not a bottom sheet with detents. Sheets stay for scoped tasks only.
  • Window controls. When the window is windowed, the system draws controls at the leading edge of the toolbar; keep leading toolbar items out of their way.
  • The menu bar auto-hides by default on iPad, so every command also lives in the interface. In iPadOS 27 it can be kept visible and is left-aligned like on Mac (secondary source). The iPad Settings command opens the system Settings app, so our settings stay a tab or sidebar item.
  • OS 27 sidebars are edge to edge again on iPad and Mac, and the Mac toolbar is uniform. Use the system sidebar and toolbar unstyled. Details and the Liquid Glass slider: OS 27 and System Surfaces.
  • Pointer. System hover and lift effects on bars and tabs; our cards get a hover effect; no information appears on hover alone. Drag and drop: dropping an address on Portfolio opens Add wallet with it filled in.

Mac: a window with a sidebar, not a big phone

The main window is a three-column window. Settings is not a tab: it is its own window under the app menu. Every toolbar item is also a menu command, because people can hide or customise the toolbar.

  • Sidebar: wallets as a filter, then Alerts. Two levels at most. It collapses when the window gets narrow.
  • Detail replaces in place. No push and no zoom on Mac. A short crossfade, none under Reduce Motion.
  • New windows are an option, not a default. "Open in New Window" in the Position menu and the context menu opens a position in its own window.
  • Alerts without push. The Alerts item shows the alert history and a note that push arrives on the phone. It is not hidden or disabled.
  • Search in the toolbar searches positions and tokens, and ⌘F focuses it.

Settings window

Opened from the app menu or with ⌘,. Minimise and zoom buttons are dimmed. The toolbar is not customisable and always shows the active pane; the window title follows the pane; the last pane is restored.

Menu bar

Menus keep their fixed order: app, File, Edit, View, then app-specific menus, Window, Help. Items are disabled, never hidden. One-word titles. macOS 27 shows fewer menu item images, so the title carries the meaning. Standard shortcuts stay standard; custom ones are few and use Command.

Accessibility on these surfaces

Follows docs/decisions/0022-accessibility.md. The wide layouts add focus groups, menu parity and window titles.

What each surface must do
SurfaceRule
Focus groupsSidebar, list, detail and toolbar are separate groups. The primary item of a group takes focus when the group does. Selecting a row never moves focus into the detail.
VoiceOverEach row is one element with the position and its range status; swipe and context actions are custom actions; headings and links are in the rotor; the cursor does not reset on live updates.
Voice ControlEvery toolbar button has a name ("Add", "Share"); rows are named by the pair.
Menu bar and toolbarEvery toolbar item is also a menu command. Toolbar buttons have tooltips. The window title says where you are.
Text sizeiPad scales with Dynamic Type and reflows. Mac has no Larger Text, so the window and the display zoom are tested.
Contrast and glassToolbars use the system look, so Increase Contrast and Reduce Transparency apply. Content stays on opaque colour blocks.
MotionDetail changes crossfade on wide layouts and under Reduce Motion; the zoom stays on narrow windows.

SwiftUI mapping

One multiplatform target, one navigation structure per width. These are sketches, not compiled.

// iPad and Mac: tabs that become a sidebar
TabView(selection: $section) {
  Tab("Portfolio", systemImage: "chart.pie", value: Section.portfolio) { PortfolioSplit() }
  Tab("Alerts", systemImage: "bell", value: Section.alerts) { AlertsSplit() }
  #if !os(macOS)
  Tab("Settings", systemImage: "gearshape", value: Section.settings) { SettingsList() }
  #endif
}
.tabViewStyle(.sidebarAdaptable)

// list and detail
NavigationSplitView { WalletSidebar() } content: { PositionList(selection: $selected) } detail: { PositionDetail(id: selected) }

// scenes: the main window with its commands, a window per position, the Mac settings window
WindowGroup { RootView() }
  .commands {
    CommandGroup(replacing: .newItem) { Button("New Wallet…") { showAdd = true }.keyboardShortcut("n") }
    CommandMenu("Position") { Button("Copy Address") { copyAddress() }.keyboardShortcut("c", modifiers: [.command, .shift]) }
  }
WindowGroup("Position", for: Position.ID.self) { $id in PositionDetail(id: id) }   // Open in New Window
#if os(macOS)
Settings { SettingsPanes() }          // opened with ⌘,
#endif

// toolbar, search, context menu, tooltips
.toolbar { ToolbarItem(placement: .primaryAction) { Button("Add", systemImage: "plus") { showAdd = true }.help("Add a wallet") } }
.searchable(text: $query)
.contextMenu { Button("Copy Address") { } }

Decisions this pass makes

The first two close open questions of the navigation map.

  1. On wide layouts, wallets are a sidebar filter. That answers the wallet switcher question for iPad, Mac and tablets. On iPhone it stays a header menu, added after the first beta.
  2. The detail is a column on wide layouts, a push on narrow ones. Zoom runs only on narrow windows.
  3. Settings on Mac is a window with four panes. On iPad it is a tab or sidebar item, because the system owns ⌘, there.
  4. New windows are opt-in from the Position menu and context menu.
  5. The menu bar lists every command, and every toolbar item is one of them. Cards and Rows stays a segmented picker; the macOS 27 .tabs style is for switching sections only.
