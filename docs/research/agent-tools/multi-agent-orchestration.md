# Multi-agent orchestration

Scope: owner-local, Claude Code on one Mac, extends [autonomy-loops](autonomy-loops.md). Binds no contributor. Claude Code docs read at v2.1.29x-era pages; items marked (secondary) are not primary sources.

## Decisions

Topology and claiming
- We use a script as orchestrator and independent `claude` sessions as workers, not agent teams, because teams are experimental, off by default, spawn only in interactive sessions (not `-p`), do not isolate teammates in worktrees, lose in-process teammates on `/resume`, and bubble all permission prompts to the lead. [1][2]
- We let one planner session (Opus, plan mode, read-only) turn an `approved` spec into `tasks.json`: each task has `id`, `role`, `workspace`, `owns` (path globs), `depends_on`, `acceptance` (commands), `status`. The owner approves the spec once; the planner needs no second approval. Workers are single-threaded inside a task, because parallel agents that split one task make conflicting implicit decisions. [3][4][5]
- We make file ownership the primary lock: a task may edit only its `owns` globs; one workspace has one writer at a time; `packages/contracts` and `packages/core` tasks run alone and first, and clients depend on the contract task via `depends_on` (then `api:sync`). A PreToolUse hook denies edits outside `owns`. Docs say teammates "own a different set of files" is the only conflict defence in teams; worktrees only isolate checkouts. [1][6]
- We claim a task with an atomic `mkdir $VOIDX_STATE/claims/<task-id>` (writes agent name, session id, pid, time inside); a failed `mkdir` means take the next task. The reaper removes a claim whose pid is dead or heartbeat is older than 30 min and sets the task back to `todo`. This is our design; Claude Code's own team task claim uses file locking for the same race. [1]
- We keep shared state in an absolute path outside every worktree, `$VOIDX_STATE` (default `~/.claude/voidx-loop/state/`, exported via `--settings` `env`), because a gitignored `.agent/` exists separately in each worktree and is not shared. [6]

Progress file and dashboard
- We keep two artefacts: `tasks.json` (machine state) and `progress/<agent>.md` (append-only log, one file per agent, no merge conflicts). A `voidx-task` shell wrapper is the only writer of `tasks.json` (takes a `mkdir` lock, changes only `status`, `note`, `updated_at`, `commit`), and agents may not edit task text or acceptance commands. Anthropic's harness uses JSON for the feature list because the model is less likely to overwrite JSON than Markdown, lets agents change only `passes`, and keeps `claude-progress.txt` as the human log next to git history. [7]
- We make `progress.md` a generated view (done / doing / next per agent), never hand-written by agents, so "one shared file" is satisfied without concurrent writes to one Markdown file. (Our design.)
- We build the dashboard as one static `dashboard.html` regenerated by a script every few seconds from `tasks.json`, each `progress/*.md` tail, and `claude agents --json --all` (fields `state`: working, blocked, done, failed, stopped; `waitingFor`; `cwd`; `name`). We do not parse `~/.claude/jobs/` (not a stable interface). Agent view alone shows state, not our done/next steps, and its row text is a Haiku summary refreshed at most every 15 s. [8]
- We tick a task `done` only when its `acceptance` commands pass in the wrapper, not when the agent says so. [7][9]

Roles
- We define roles (backend, frontend, ios, android, ui-ux, motion, qa, integrator) as subagent files in the local plugin with narrow `tools`, pinned `model`, `maxTurns`, workspace-specific skills and a `memory: local` scope, because definitions are the documented way to restrict tools and keep verbose output out of the main context; the same file works as a teammate definition (but `skills` are not applied to teammates). [10][1]
- We do not rely on "senior persona" prompts for quality: no primary source measures that benefit. Anthropic names testing, QA and cleanup agents only as untested future work. The measurable gains are tool restriction, file ownership, and a reviewer that did not write the code. [7][9]
- We run `qa` and `spec-verifier` read-only and from a fresh session, ui-ux and motion as reviewers against ADR 0022/0023 gates, not as parallel implementers of the same screen. [9][3]

Handoff, merge, failure
- We start every worker with the Anthropic session routine: `pwd`, read git log and its progress file, read `tasks.json`, run the init/health check, then take one task; end with commit plus progress entry, leaving the branch mergeable. [7]
- We merge locally and never push: an `integrator` session merges finished task branches into `integration/<spec>` in `depends_on` order, runs `bun run check --affected`, and stops on a conflict that touches non-owned files. The owner reviews and pushes ([AI_POLICY.md](../../../AI_POLICY.md) kept). Merge order is our design; practitioners report each merge changes the base for the others (secondary). [11]
- We retry a failed task at most twice with the failing log path in the prompt, then set `blocked`. A Stop hook blocks at most 8 times before Claude overrides it. [12]
- We stop and ask the owner on the AGENTS.md list (unknown address or ABI, new dependency, core change, unapproved plan, two docs disagree) plus: ownership collision, third failure, budget cap hit. The worker sets `blocked` with the question; the `agent_needs_input` hook notifies the owner. [8]

Width
- We run 3 workers by default and at most 5, only when their `owns` sets are disjoint and at most one touches Xcode and one Gradle, because Anthropic advises 3-5 teammates ("three focused outperform five scattered"), usage scales about linearly with agents (multi-agent about 15x a chat), and ten parallel sessions burn quota about ten times faster. Above 5 conflict and merge cost reportedly grows faster than speed-up (secondary, no benchmark). [1][8][13][11]
- We start each worker's cost cap at `--max-budget-usd` per task and a global daily cap in the launcher. [14]

## Facts that constrain us

- Agent teams (experimental): task states pending / in progress / completed with dependencies, self-claim with file locking, mailbox JSON in `~/.claude/teams/`, one team per session, no nested teams, status can lag, teammates may stop early; hooks `TaskCreated`, `TaskCompleted`, `TeammateIdle` exit 2 to block. Teammates do not inherit `dontAsk`. [1]
- Agent view: research preview (May 2026); `claude --bg` cannot be combined with `-p`; background sessions move into their own worktree before editing; supervisor keeps them alive across closed terminals and sleep, not across shutdown; `agent_needs_input` and `agent_completed` hook types. [8]
- Worktrees: `-p --worktree` runs are never cleaned up; `${CLAUDE_PROJECT_DIR}` stays at the main checkout, hook `cwd` is the worktree; isolation checks block edits and git redirects into the main checkout but not `cp` or shell redirects; permission approvals saved to the main `.claude/settings.local.json` apply to all worktrees. [6]
- Subagents nest up to 3 levels; default cap 20 concurrent; `isolation: worktree` per definition. Dynamic workflows run up to 16 concurrent agents, 1,000 per run, and suit audits and mechanical migrations, not stateful feature work. [10][15]
- Cross-session messaging (v2.1.224+): same-machine socket, plain text, cannot grant approval or change config; a `-p` worker needs `crossSessionInbound: accept` in its `--settings`. Optional; state files carry coordination instead. [16]
- Anthropic multi-agent research: orchestrator-worker, about 15x chat tokens, token use explains about 80% of quality variance, and coding is named a poor fit because of dependencies. [5]
- Cognition (2025-06-12): share full traces; actions carry implicit decisions; default to a single-threaded agent. Position predates current models. [3]
- Codex cloud and Copilot coding agent: not read in depth; Codex docs give each cloud task its own workspace and state no concurrency limit. [17]

## Conflicts with committed and existing docs

- [autonomy-loops](autonomy-loops.md) says "at most two or three worktrees" and "no agent teams, agent view or `/batch`": this note raises the ceiling to 3 default / 5 max and adds agent view as read-only monitoring; agent teams stay off. Owner to decide; autonomy-loops not edited here.
- autonomy-loops keeps handoff in `.agent/progress/<slug>.md` per worktree: not shared across worktrees; replaced here by `$VOIDX_STATE`.
- [agent-context](../../concepts/agent-context.md) lists "wide fan-out and agent teams" as not used: consistent for teams, strained by 5 workers.
- ADR 0024 "No autonomous PRs or comments": kept; integration stops at a local branch.

## Open questions

- Whether `claude -p --worktree` workers show in `claude agents` (needs `--bg`, which excludes `-p`); if not, the dashboard reads `state/` only. Test in M0.
- Whether a PreToolUse ownership hook from `--settings` applies inside subagents and worktrees as expected.
- Real quota burn of 3 vs 5 workers on the owner's plan; measure per spec, as autonomy-loops already plans.
- Cognition-style arguments against parallel writers have no 2026 follow-up; evidence on agent count is anecdotal.
- Cursor background agents and Copilot coding agent not researched first-hand.
